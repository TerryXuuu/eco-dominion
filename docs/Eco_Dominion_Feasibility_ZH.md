# Eco Dominion 可行性报告

原始中文名称：生态霸权。项目目标：将原始双人卡牌沙盘规则实现为在线 PvP 平台，支持多用户注册、多场对局并行与社区交流。课程开发预算为 16 小时，不包含环境搭建和最终部署。

## 一 可行性结论与名称

**技术上可行。** 本项目为双人、轮流行动、有限阶段的卡牌游戏，适合用明确的状态机和服务端裁判实现。公共牌库、区域权重、共享稳定度、费用与胜利检查均可保存为结构化数据。多用户支持意味着平台可同时容纳多场双人对局，并不改变原规则的双人设定。

**16 小时可以作为核心平台的集中开发目标，但不能作为生产就绪承诺。** 该计划依赖已有规则引擎与卡牌数据、已准备好的工具及云服务账户，以及负责人及时确认数字规则。实际验收以功能与测试结果为准；超过预算仍未通过时，应记录超时和阻塞，不得宣称已经完成。

两份原始文档的正文标题均为“生态霸权 Eco Dominion”。因此 Eco Dominion 可保留为英文项目名，中文沿用“生态霸权”，不需要重新翻译。建议首次出现时写作“Eco Dominion（生态霸权）”，后续正文采用“生态霸权”；报告和课程标题可保留英文名称。

## 二 原始需求与实现边界

依据《生态霸权 完整规则手册 v1.0》和《生态霸权 全卡牌图鉴 v1.0》，游戏采用公共共享牌库，无需玩家自行构建卡组；战场为森林、水域、荒野、领域四个公共区域。规则规定六阶段依次执行：刷新、抽卡、全局事件、部署、战术、区域结算。

| 原始要求 | 在线实现要求 |
|---|---|
| 双人对战与共享牌库 | 服务端洗牌、抽牌与记录；对手无法看到隐藏手牌或牌库顺序 |
| 15 种物种、6 种战术、5 种干扰、10 种事件 | 全部 36 种卡牌进入数据目录与效果测试，不缩减核心卡池 |
| 主牌库 74 张，事件库 20 张 | 分别管理抽取、弃牌与重洗；牌库耗尽不判负 |
| 起手 5 张，手牌上限 7 张 | 超限时暂停普通操作，由相应玩家完成弃牌选择 |
| 生态能量与预备能量 | 先校验支付条件，再原子执行效果；预备能量仅用于战术和干扰 |
| 权重、共享稳定度与联动 | 统一计算控制权、加成及惩罚，避免客户端自行决定结果 |
| 统治胜利或终局计分 | 明确检查时点与回合编号；结果固定后再更新战绩与排名 |

用户另行提出的注册、对局服务和社区属于平台需求，不是原卡牌文档已经定义的功能。账户、权限、匹配、排名、举报及审核流程需要在本课程中补充设计。

## 三 规则确认是首要前提

原始文本仍存在直接冲突和未定义的边界。以下内容是开发前需要确认的重点；现有数字规则草案仅为建议，不能替代负责人批准。

| 重点问题 | 原文依据 | 建议与影响 |
|---|---|---|
| 首回合能量 | 初始上限为 1，刷新再增加；图鉴却称 8 费传说第 8 回合登场 | 建议第一次刷新后为 1；确定开局状态与个人回合对应关系 |
| 示例费用超支 | 第 6 节示例支付 2 费和 3 费，超过 4 点可用能量 | 无预备能量时应拒绝后一次出牌；不能先执行再允许负能量 |
| 永久权重 | 第 4.1 节称只增不减，第 2.6 节却规定永久惩罚扣减 | 建议独立记录区域惩罚；明确迁移、重复结算与控制权重算 |
| 对手响应窗口 | 第 2.5 节禁止对手插入出牌，解释却称临时效果能阻止对手斩杀 | 建议保留无插入式响应，修正误导说明；新增窗口属于正式规则修改 |
| 第 8 回合与胜利时点 | 开头称第 8 回合结束前；胜利表称双方各完成 8 回合 | 建议每人 8 个个人回合，在区域结算时检查统治，最后再终局计分 |
| 被动、联动与稳定度 | 雄鹿持续贡献、蜥蜴联动与非正稳定度禁用之间的关系不完整 | 明确贡献重算与禁用顺序，避免自我触发或循环判断 |

完整的 26 项规则审核及中英文冲突说明见已有项目包。S01 应将确认后的规则版本、真实批准记录和内容摘要固定下来。未批准时可以完成账户与界面工作，但不得将未确认规则标记为最终验收通过，亦不得开放已验证排名玩法的承诺。

## 四 技术方案与功能范围

采用一个 Next.js 应用承载界面与服务端接口；Neon PostgreSQL 保存账户映射、对局、指令、结果、排名及社区数据；Neon Auth 处理身份认证；GitHub 保存代码和提交历史；Cursor IDE Agent 辅助四个开发单元。Vercel 为后续托管目标，本计划不执行最终发布。

对局采用已认证 HTTP 指令和版本轮询。服务器根据身份确定玩家席位，校验阶段、费用、目标、规则版本及对局版本。在数据库事务内锁定对局，使用指令唯一编号处理重试，保存新状态与回执后提交。重复发送不得重复抽牌、扣费、结算或更新排名。返回给每名玩家的数据必须经过席位过滤。

断线后通过数据库恢复状态。截止时间持久化，并在读取或操作时检查；无访问的对局在下一次访问时推进。若要求无人访问时也按墙钟时间自动推进，需要额外调度机制，不能将其当作当前方案已实现的能力。轮询频率须在实际运行中调整，不能从设计直接推导并发容量。

16 小时内目标包含注册、登录、退出、找回账户、个人资料、权限、私人房间、休闲匹配、完整卡牌对局、重连、认输、战绩、回放、基础排名，以及文字动态、评论、点赞、好友、关注、屏蔽、站内通知、举报和管理员审核。

高级卡牌美术、图片上传、自定义多因素认证、复杂赛季和赛事、大规模压测、长期平衡评估及运营强化不纳入本次压缩开发。此边界不改变原始游戏卡池与基本玩法。环境安装、云项目创建、生产凭据配置、域名和最终上线由课程之外处理。

## 五 16 小时预算与验收判断

课程由四个 4 小时开发单元组成：S01 账户与规则基础，S02 在线 PvP，S03 社区与用户管理，S04 集成验证与修复。没有额外计入的环境搭建、最终部署或隐藏缓冲课时。

目前已有准备包中的参考引擎通过 39 项测试，包括种子对局不变量检查；会话工作流通过 5 项测试。这些是已有基础代码的证据，不代表 Next.js 应用、Neon 数据库接入、真实用户 PvP 或社区功能已完成，也不能证明玩法平衡。在线应用的验收证据需在四个开发单元中实际生成。

最终至少观察两名独立用户完成注册和完整对局，检查重连、重复指令、过期版本、隐藏信息、结果和排名的一次性更新；再验证社区所有权、屏蔽、举报和管理权限。类型检查、核心测试和本地生产构建必须通过。每个开发单元保留 Git 回滚检查点、实现提交、测试证据和 TASKS 状态。

**实施建议：** 按 16 小时开展集中构建，复用既有引擎并优先确认规则；以四个单元的验收结果决定是否达到核心平台目标。公开运营能力需要后续部署和真实运行验证，不能由课程时间或本地构建成功代替。

## 自动运行验证

架构 2.3 以自动模式为默认。当前控制器通过 9 项隔离自动编排测试与 5 项既有工作流测试，包括自动读取、独立提交、下一单元、失败阻塞、工作保留、预算和恢复。测试使用临时目录中的模拟 Agent，不代表已在你的 Cursor 登录账户上实际运行。已有规则引擎回归仍须通过；四个应用实现单元仍为未验收状态。真实规则批准、必要凭据和实际浏览器证据不能由自动化伪造。
